# ADR-0042: One active digital copy per customer account

## Status
Accepted for Phase 1, 2026-10-24. Supersedes ADR-0026's allowance of multiple new active purchase sources for the same customer/edition. Historical sources remain immutable and independently refundable.

## Context
V045 consolidated duplicate purchases into one library identity while silently adding paid grants. Quantity one in a cart did not protect against a second order or concurrent deferred captures. V072 introduced genuine `PENDING_PAYMENT` orders with `PENDING` payments, including transfers. Their carts are already `CHECKED_OUT`; locking only the active cart cannot coordinate later payment approval.

## Decision
V076 implements the invariant in the public PostgreSQL Database API and defensive item/payment/grant triggers. Java retains Controller → Application Service → JDBC Gateway and Spring transactions.

Owned means an ownership identity with at least one `digital_grant.state='ACTIVE'`. A retained identity with only REVOKED grants is not owned. An open source also blocks purchase: a digital order item for the same customer/edition, an order other than CANCELLED with `finalizado_en IS NULL`, and a PENDING or APPROVED payment. Paid digital orders in their six-minute cancellation window can be both owned and open; owned takes error precedence. Finalized digital orders remain owned through their active grant. Finalization alone never permits repurchase. Rejected/cancelled/refunded purchases do not block after all active grants are revoked. Approved but revoked sources still block while open until cancelled/finalized; ordinary cancellation revokes and closes atomically.

Acquire `pg_advisory_xact_lock(hashtextextended('digital-purchase:' || cliente_id, 0))` before cart/order/master locks. Cart add, quote projection, quoted/billed/idempotent acceptance, checkout execution, order-line creation, payment approval and ACTIVE grant transitions use this same transaction-scoped lock. Different attempt keys and different cart generations must coordinate. READ COMMITTED routines issue separate statements after waiting so they observe the winner's commit. A hash collision can only cause additional serialization. Lock lifetime is the Spring transaction; there is no session lock or Java lock. Existing cart/master/inventory locks still protect quantities, prices, discounts and stock.

The cart quote takes the lock and projects a fresh reason instead of throwing, allowing clients to display/remove stale lines. Acceptance and execution raise before commercial effects. Explicit expected cart IDs are checked for digital conflicts before active-cart rejection, giving the concurrent loser P6002/P6003. Same-key receipts replay before eligibility checks; they do not re-charge. Deferred approval excludes its own order from ownership/open-source checks. Same-item grant reconciliation is idempotent; a different active source raises and rolls back payment capture. Revocation needs no acquisition lock: it can only remove access, preserves existing refund lock ordering, and concurrent acquisition sees either the old conflict or the committed revocation.

P6002 (`DIGITAL_ALREADY_OWNED`) and P6003 (`DIGITAL_PURCHASE_PENDING`) map to HTTP 409 in foundation. REST `code` and cart `unavailabilityReason` retain the canonical SQLSTATE convention; symbolic names are documentation labels. Spanish title/detail live in the common error handler and the [API amendment](../api-amendments/2026-10-24-single-digital-copy.md).

V076 audits legacy duplicate ACTIVE source groups with a NOTICE. It adds nonunique lookup indexes, no uniqueness constraint that could reject historical rows, and never revokes a paid historical acquisition to make a constraint fit. Existing multiple ACTIVE grants remain readable, same-item retries remain safe, and cancellation can revoke each source. Only new ACTIVE sources/reactivations are rejected. Production counts require running the preflight against production; this phase uses disposable local databases and does not inspect or mutate production.

`GET /api/v1/me/digital-eligibility?editionIds=...` accepts 1–50 positive IDs like favorites status. PostgreSQL returns each ID once in first-occurrence order with owned, nullable ownedItemId (library link), pendingOrder, nullable pendingOrderId (order link), inCart and purchasable. Missing, physical or inactive editions are not digitally purchasable. inCart is informational; an otherwise eligible line can be purchased from the cart. This read is a point-in-time advisory projection; checkout revalidates. Account identity always comes from the authenticated subject.

## Consequences
One customer can acquire a digital edition once until cancellation/refund removes access and closes the source. Physical purchase quantities, inventory, offers, pickup, refunds and six-minute finalization retain their existing routines. Repeated digital cart add is idempotent at quantity one (the prior V032 routine actually rejected repeated adds). Existing legacy pending duplicates must be cancelled down to one before approval. Legacy duplicate paid sources need review for refunds; no automated financial correction is introduced.

## Validation
The full Maven suite validates API validation/security, OpenAPI coverage and Spanish conflict mapping. `run_ci_gates.sh` runs SQL invariant/rollback/idempotency/repurchase/physical checks, independent-session approved and pending checkout races, and real HTTP → Spring → JDBC races and eligibility tests. `digital_single_copy_upgrade_gate.py`, on a separate empty disposable database, verifies V075→V076 with two existing ACTIVE grants and duplicate pending orders, unchanged historical grants, same-item replay, grant/reactivation rejection and capture rollback. The existing lifecycle, stock, offer and cancellation gates remain regression coverage.

Phase 2 API correction (2026-10-24): `pendingOrderId` is the nullable string ID for `/orders/{id}`, taken from the same blocking source as `pendingOrder`. When legacy duplicates exist, the lowest blocking order ID is returned deterministically. It can coexist with `ownedItemId`; ownership keeps presentation/error precedence. No order from another customer is exposed. V076 is amended under explicit authorization because it has not been committed or deployed; locking, command idempotency and all business gates remain unchanged.
