# ADR 0052: Creación condicional de ofertas sobre la ruta existente

Fecha: 2026-11-01. Estado: aceptado para implementación local; sin publicación ni cambios de producción.

La oferta de una edición tiene una fila única que conserva promociones vencidas o inactivas. El PUT existente es un upsert y los detalles públicos ocultan filas que ya no aplican. Un operador que debe crear una campaña sin reemplazar ninguna fila anterior no puede demostrar ausencia mediante el detalle público, y una consulta previa no elimina la carrera con otro escritor.

La respuesta de la búsqueda ADMIN existente incorpora `offerRowExists`, calculado por una función de Database API que exige actor ADMIN y considera todas las filas. El mismo PUT acepta un modo condicional cuando recibe `If-None-Match: *`, `X-Expected-Base-Price` y `X-Expected-Stock`; `NONE` representa una edición digital sin stock físico. Las tres cabeceras se requieren juntas. Sin cabeceras se conserva el upsert anterior.

V098 incorpora `sp_edition_offer_create_if_absent`. La rutina exige ADMIN, bloquea la edición con FOR UPDATE, el libro con FOR SHARE y el inventario físico con FOR UPDATE NOWAIT. Los comandos de inventario existentes toman inventario antes de que su trigger solicite SHARE sobre la edición: si hay contención, la creación falla con P1001 y libera la edición, en vez de esperar y formar un interbloqueo. Bajo esos bloqueos verifica estado público, portada CDN, precio base, stock esperado y ausencia de cualquier fila de oferta, y luego delega en `sp_edition_offer_set`. Spring conserva el límite transaccional. Controllers y Services no contienen SQL de negocio; JDBC únicamente invoca Database API. Las precondiciones fallidas conservan P1001/HTTP 400 y no alteran los mapeos aprobados. Ambas rutinas nuevas revocan EXECUTE de PUBLIC y conceden el acceso de ejecución al rol de runtime existente.

La herramienta de campaña envía siempre estas condiciones y vuelve a comprobar las filas por API. Dos creadores concurrentes de la misma edición no pueden sustituirse: uno crea y el otro falla. Los bloqueos también permiten comprobar cambios concurrentes del precio base y stock antes de crear. No se promete transacción de toda la campaña: cada PUT puede confirmar por separado y un fallo posterior deja una campaña parcial. Tampoco se impide que un administrador use posteriormente el upsert legítimo para editar una oferta existente. El diario durable permite revisar respuestas inciertas sin reintentos ni rollback ciegos.

La creación protegida requiere desplegar juntos el campo ADMIN, la semántica de cabeceras y V098. Una versión anterior sin `offerRowExists` hace que la herramienta rechace el preflight. El contrato anterior sin cabeceras conserva su comportamiento. Gates SQL, HTTP y cuatro carreras con barreras de bloqueos comprueban ausencia, filas vencidas/inactivas, permisos, compatibilidad, cambios concurrentes de base/stock y la ausencia de interbloqueo con el comando real de inventario.
