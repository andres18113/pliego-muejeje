# ADR0028 — Authoritative cart base prices and savings

Accepted, 2026-10-06.

The effective offer price already drives live cart quotes, tax and checkout. The cart lacked base prices and savings needed to present offers. V051 adds `pliego.fn_cart_offer_quote(actor)` as an additive Database API projection around the unchanged `fn_cart_quote` and `fn_edition_offer` routines. PostgreSQL computes original unit/line prices and unit/line savings using the existing offer eligibility and effective pricing logic, within one statement snapshot. No promotional calculations are persisted.

The new REST item fields are `originalPrice`, `unitSavings`, `originalSubtotal` and `lineSavings`; `currentPrice` and `currentSubtotal` retain their values. Summary fields are `originalSubtotal`, `savingsTotal` and `currentSubtotal`. Existing `subtotal` remains discounted merchandise, and `totalCurrent` remains the legacy total including tax. The invariants are `originalSubtotal - savingsTotal = currentSubtotal` and `currentSubtotal + taxAmount + shippingAmount = total`.

Java forwards and formats the database values. The frontend adapter accepts the additive fields, rejects malformed supplied money, and preserves older responses that omit them. A presentation view model formats server amounts and reports field availability, without deriving discounts, tax or eligibility. Existing cart and checkout pages retain their layout and existing subtotal consumer behavior; Claude can consume the projection for the requested presentation pass.

Expired, future, deactivated or suppressed offers automatically project zero savings on the next authoritative read. Existing cart refresh-on-mount and checkout revalidation continue to request current server prices. Checkout, stock, digital quantity rules and historical order snapshots are unchanged.

The requested lifecycle extension adds V052–V054. Four nullable original/savings columns on `pedido_item` capture the existing offer projection when a new item is inserted during checkout. The existing immutable paid unit/line amounts and paid header remain unchanged. Existing item update/delete guards and the new paid-order insertion guard protect these snapshots; a parent `FOR UPDATE` lock serializes capture with the payment foreign-key lock to reject concurrent historical append attempts. Original order summaries aggregate only these immutable stored items. No current catalog or offer lookup is used to render history.

Historical helpers `fn_order_offer_pricing` and `fn_order_item_offer_snapshots` enrich the ownership-checked order projections. Checkout/confirmation, order lists and detail expose original/savings/current amounts and `pricingSnapshotAvailable`; full detail provides per-item values. Older orders remain unknown (`original*`/savings null and availability false), while their actual paid amounts stay available. The order list also forwards the existing historical subtotal/tax/shipping breakdown. Cancellation, refund, expiry and idempotent replay do not change the stored pricing. Typed order adapters and a separate historical presentation view model consume these values without reconstructing them from today's catalog.
