Frontend integration is intentionally a separate handoff. Existing hand-written `emailActions.ts` retains its prior behavior and must be updated by the frontend owner together with its callers before shipping the new flow.

- Registration201 body stays `{userId,customerId,state:"PENDING_VERIFICATION"}`; cookie is browser managed. Never store continuation or mail token in local/session storage or put continuation in a URL.
- `POST /api/v1/auth/registration-session` needs credentials included and marker1.200 is LoginResponse plus nullable returnTo;202 contains `state` equal PENDING_VERIFICATION, REFRESH_REQUIRED or RETRY_LATER;204 means stop waiting and use ordinary sign-in/recovery. RETRY_LATER sends no Set-Cookie: retain the continuation and retry after the Retry-After seconds; never treat it as a terminal credential or authentication.
- `POST /api/v1/auth/verify-email` must send marker1 because an HttpOnly cookie may be present.200 installs a session and returns the same session shape;204 verifies without authentication and sends no Set-Cookie, including when the IP quota denies exchange. Existing400 invalid-link behavior remains.
- On REFRESH_REQUIRED use existing cross-tab session lock and `/refresh`; allow a brief retry for another tab's in-flight response. Do not manufacture authenticated state from202. If refresh cannot recover a cookie, offer normal login.
- Use response returnTo only after runtime validation and authorization appropriate to its destination. `registrationSessionSchema` and `registrationSessionStateSchema` provide runtime validation; no visual/auth state behavior was changed here.
- Poll only on useful lifecycle events or at intervals of at least6 seconds, stop after terminal outcomes, and preserve the existing session mutation lock/timeouts. Handle the uncertain result of a lost verification response through normal session restoration before requesting a new link.
