# Verificación de correo al abrir el enlace

El recorrido de registro es **Revisa tu correo → abrir el enlace → Correo verificado → volver a donde estabas**. La página comprueba el enlace automáticamente; no pide una segunda confirmación con un botón «Verificar correo».

Mientras responde el servidor, muestra «Verificando tu correo» y el estado accesible «Estamos comprobando el enlace…». Solo una respuesta 204 de `POST /api/v1/auth/verify-email` permite mostrar «Correo verificado». Tras una confirmación breve de 1,2 segundos, continúa automáticamente hacia el destino validado del enlace (`from`); «Continuar» permite hacerlo antes. Sin destino válido, abre el inicio (`/`).

El contexto se conserva en la URL del flujo y del correo: búsqueda, filtros, ficha del libro y fragmento de navegación. No se guarda un destino global que pueda mezclarse con otra cuenta o navegador. `safeAuthReturnHref` conserva únicamente rutas internas admitidas; direcciones externas y páginas administrativas o del propio login/verificación vuelven al inicio. El cambio utiliza `replace` para no conservar la pantalla de verificación como paso adicional al retroceder. Un enlace nuevo o salir de la página cancela la redirección anterior; los errores y resultados inciertos no redirigen.

La verificación no inicia sesión automáticamente ni autoriza compras. Si el destino es privado, se mantienen los controles de acceso existentes; una persona sin sesión ve el acceso al login y conserva el destino para continuar después. Una sesión de cliente vigente continúa con sus permisos habituales.

La página reutiliza la API de identidad existente. Captura el token del fragmento en memoria y retira el fragmento del historial con `replace`. El GET de la página no consume el token: el navegador emite el POST de verificación. Un enlace ausente, inválido, vencido o utilizado muestra la recuperación correspondiente. Una respuesta perdida muestra un resultado incierto y permite iniciar sesión o solicitar otro enlace, sin anunciar un éxito que no se confirmó.

Cada token tiene una única ejecución HTTP durante esa vista, incluso bajo Strict Mode, cambios de parámetros, reaperturas del mismo enlace o una secuencia A → B → A. Se conserva su promesa original en memoria, incluidos los resultados inciertos; nunca se guarda el token en el almacenamiento del navegador ni en la caché global de consultas. La respuesta tardía de A no sustituye el estado de B. Un enlace diferente puede verificarse en la misma página.

El restablecimiento de contraseña mantiene su confirmación explícita: abrir el enlace solo presenta el formulario; el token se consume al enviar y confirmar la contraseña nueva. No cambian contratos REST, reglas PostgreSQL ni el esquema.

Pruebas: `EmailActionPages.test.tsx` cubre envío automático, carga, éxito, errores, Strict Mode, reaperturas, respuestas fuera de orden y ausencia de reintentos de resultados inciertos. `VerificationReturn.test.tsx` comprueba el retorno validado, reemplazo del historial, destinos privados y la prioridad de la navegación del usuario, incluso mientras carga otra página. `email-actions.spec.ts` comprueba el recorrido en navegador, la conservación del contexto desde registro y la separación con recuperación de contraseña. `registration-return.spec.ts` mantiene la prueba real opcional de registro/correo/inicio de sesión, que requiere su fixture local explícita.
